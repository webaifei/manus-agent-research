## 一、极客公园对谈（A）

**Agent 的定义是三段，不是两段**——这是全文最有价值的一句：

> 聊天机器人和生成式工具「通常只有两个角色：用户和模型」。而 Agent「除了用户和模型，还引入了第三个关键元素——**环境**」。
> 「在 Manus 这里，我们的目标是让 Agent 出现在**虚拟机甚至整个互联网**中。」（[原文](https://w.geekpark.net/news/352981)）

这一句直接解释了为什么 Manus 要做云 VM——**不是工程选择，是定义上的必要条件**。没有环境就不是 Agent。

**AGI 的定义与路径**：
> 「AGI 是一种能利用 AI 模型的通用能力，在不经过特别设计的情况下完成许多任务的系统。」
> 「我们认为『Agent coding』其实是通往 AGI 的一条路径。它不是一个垂直领域的能力，而是如果你把它赋予计算机，它几乎能在计算机上做任何事。」

**「瓶子里的大脑」**：
> 「现在的旗舰模型已经非常惊人了，几乎是『超人』级别的……但我认为，模型仍然像是『瓶子里的大脑』，如果想真正发挥力量，就必须让它们与真实世界交互。」

**瓶颈不在智力**（对应他自己那篇博客没说的部分）：
> 「现在几乎所有东西都是为人类设计的……网页工具，它们就像小游戏一样，没有提供 API 或标准接口。验证码 CAPTCHA 无处不在，处处在拦截 Agent。」
> 「我觉得这并不是技术问题，而是更像是一种**制度性限制**。这不是像我们这样的 Agent 创业公司能够单独解决的事情。」

**两条主线**（2025-08 时点的战略）：
1. 用多 Agent 协作把**执行规模做宽**（上百个并行子 Agent = Wide Research）
2. 给 Agent 打开更大的**工具面**——不绑死在预置 API，像程序员一样调用开源生态、装库

**「工具的网络效应」**——这个概念在官博里没有：
> 例子：图表里显示中文/韩文时字体出错。有人会写硬编码规则（「输出韩文时用哪种字体」），「但这种方式会让系统越来越僵化」。
> Manus 的做法是给系统加一个能力：**查看图像**。结果模型会在生成后自己检查、发现错误、自动修正。
> 「**增加工具的灵活性比硬编码规则能解决更多的问题。**」

**一次会话、一个共享上下文**：
> 「搭建一个网站本身其实不难，难的是如何确保数据的可靠性和准确性。所以我们认为，最好能在**一次会话、一个共享的上下文**中完成整个流程。」（研究 → 见解 → 成果）

**一个反直觉的观察**：
> 「通过大量用户调研，我们发现用户在使用之后，他们反而**工作得更多了**。因为他们变得更高效了。」

**经营数字**（2025-08）：RRR 约 **9000 万美元**。注意肖弘在即刻的澄清：RRR = 当月 Revenue × 12，**不等于 Cash Income**，年付只能算预存款。

## 二、E2B 案例（B）——架构分层的原始出处

**planner → executor 两层，这里写得最直白**：

> 「Manus is not a single LLM agent—it's a more complex coordination system. Prompts go first to a **planner agent** that decomposes them into a sequence of subtasks. Then, **executor agents** carry them out using a variety of tools.」（[原文](https://e2b.dev/customers/how-manus-uses-e2b-to-provide-agents-with-virtual-computers)）

**工具数的原始出处**——联合创始人张涛（Tao Zhang）原话：

> 「Manus doesn't just run some pieces of code. It uses **27 different tools**, and it needs E2B to have a full virtual computer to work as a real human.」

这条和泄露 prompt 的 V4 版（2025-04，27 工具）**对上了**。

**弃用 Docker 的真实原因**（比"太慢"更准确）：
> 「they tried Docker. The problem was, it was really slow (**10 - 20 seconds to spawn**), but most importantly, Docker, as a container solution, **doesn't have full functionality of an operating system**. And Manus team needed real operating system so the agent can perform actions like **installing apps or Python packages**.」

即：**慢只是次要问题，主要问题是容器不是完整 OS**——装不了包，而"能在沙箱里现装现用"正是第 3 层动作空间的前提。

**其他事实**：
- E2B 用 **Firecracker microVM**；新沙箱约 **150ms** 启动
- **付费用户沙箱可保存最多 14 天**；沙箱会话可跑数小时
- 需要**暂停/恢复**沙箱的三个场景：要和用户确认、需要网站凭证、**要过 CAPTCHA**（「verify you are human」）
- Manus **自托管** E2B（跑在自己的机器上）
- 自建成本：**3–5 个全职 infra 工程师**，数月工作量
- 未来方向：扩展到 **Windows 和 Android**（virtual Android）

## 四、philschmid（B）——术语体系与细节

**他给这套实践补了一套命名**（[原文](https://www.philschmid.de/context-engineering-part-2)）：

- **Context Engineering** 包含四件事：Offloading（移到外部系统）、Reduction（压缩历史）、Retrieval（动态加信息）、**Isolation（隔离上下文）**
- **Agent Harness**：包住模型的那层软件——执行工具调用、管理消息历史循环、处理上下文工程逻辑
- **Context Rot**：上下文填满时性能退化，**即使远未到达技术上限**；「有效上下文窗口常常远小于宣称值，目前多数模型 **< 256k**」
- **Context Pollution**：无关、冗余、冲突的信息干扰推理
- **Context Confusion**：模型分不清指令/数据/结构标记，或遇到逻辑上互斥的指令

**压缩的优先级**（很实用的一条）：

> **Prefer raw > Compaction > Summarization only when compaction no longer yields enough space.**
> - **Compaction（可逆）**：剥掉「因为环境里已经存在」而冗余的信息。例：写了 500 行代码，历史里只留路径（`Output saved to /src/main.py`），不留内容。
> - **Summarization（有损）**：超过阈值（如 128k）时用 LLM 总结；**总结时保留最近几次工具调用的原格式全文**，「ensures the model maintains its rhythm」。

**多 agent 的原则来自 Go**：

> 「Share memory by communicating, don't communicate by sharing memory.」
> - **离散任务**：起全新 sub-agent，只传具体指令
> - **复杂推理**：只有 sub-agent 必须理解整条轨迹时才共享全量上下文（例：需要看之前所有失败尝试的 debug agent）
> - 「Treat shared context as an expensive dependency to be minimized, **forking context breaks the Cache**」

**三层动作空间的具体内容**（转写里只说了有分层，这里给了定义）：

| 层 | 内容 |
|---|---|
| Level 1（Atomic） | 模型看到约 **20 个核心工具**（`file_write` / `browser_navigate` / `bash` / `search`…），稳定、cache 友好 |
| Level 2（Sandbox Utilities） | 不给每个工具单独定义，而是在 `bash` 里通过 CLI 调用；Manus 有 `mcp-cli <command>`，**把工具定义留在上下文窗口之外** |
| Level 3（Code/Packages） | 复杂逻辑链不来回问模型，给库/函数让 agent 写脚本一次跑完 |

**Agent as Tool + MapReduce**：
> 「Don't over-anthropomorphize your agents. You don't need an 'Org Chart' of agents (Manager, Designer, Coder) that chat with each other.」
> 主模型调 `call_planner(goal="...")`，harness 起一个临时 sub-agent loop，**返回结构化结果**（如指定 JSON schema），「instantly usable without further parsing or conversation」。

**几条实践结论**：
- **不要用 RAG 管理工具定义** —— 「creates a shifting context that breaks the KV cache and confuses the model with 'hallucinated' tools」
- **不要训自己的模型** —— 「We are living the Bitter Lesson」；在特定动作空间上训 RL 等于「locking yourself into a local optimum」
- **设 Pre-Rot Threshold** —— 1M 窗口的模型常在 < 256k 就退化，别等 API 报错
- **todo.md 的历史** —— 「In early versions, Manus used a todo.md file that was constantly rewritten. This **wasted ~30% in earlier versions**」→ 改成返回结构化 Plan 对象的 Planner sub-agent
- **Intern Test** —— GAIA 这类静态基准「saturated quickly and didn't align with user satisfaction」；改用**计算上可验证**的任务（代码编译过了吗？文件真的存在吗？）
- **「随机梯度下降」** —— 「Manus was rewritten **five times** in the last six months. LangChain re-architected Open Deep Research **four times**. This is normal.」
  - 「**If your harness is getting more complex while models improve, you are likely over-engineering.**」

**他的结论段与转写完全一致**：
> 「their biggest performance gains didn't come from adding complex RAG pipelines or fancy routing logic. The gains came from **removing things**.」
> 「They removed complex tool definitions in favor of general shell execution. They removed 'management agents' in favor of simple structured handoffs.」
